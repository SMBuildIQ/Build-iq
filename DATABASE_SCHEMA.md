# Database schema

ORM: Prisma 5. Provider today: **SQLite** (`DATABASE_URL=file:./dev.db`). Production target: **PostgreSQL** — the
schema is provider-agnostic aside from the `datasource` block; see ARCHITECTURE.md for the migration note.

Full model source: `prisma/schema.prisma` (grouped with section comments matching the headings below).

## Tenancy & identity

`Organization` (tenant) → `Location` (branch) · `User` (global identity, can hold multiple `Membership`s) →
`Membership` (user↔org, one per pair, carries `MembershipRole[]`) · `Role`/`Permission`/`RolePermission` (RBAC,
`Role` is org-scoped, `Permission` is the fixed system catalog) · `Invite` · `LoginAttempt` (lockout counters).

## Org configuration

`Department`, `CostCenter`, `PolicyRule` (deterministic approval/bid-count/international/substitution rules —
brief §18), `NegotiationAuthority` (AI autonomy limits, one per org, `autoNegotiateEnabled` defaults false).

## Suppliers

`Supplier` (org-scoped, approved/restricted status, rolling performance metrics) → `SupplierContact`.

## Purchasing

`PurchaseRequest` → `PurchaseRequestLineItem`, `PurchaseRequestComment`, `PurchaseRequestStatusEvent` (audit
trail of every status transition) → `RFQ` → `RFQLineItem`, `RFQSupplier` (per-invited-supplier communication
state + `secureToken` for the portal) → `RFQMessage` (Q&A thread) → `Quote` → `QuoteLineItem`,
`QuoteExtractionField` (field-level AI extraction traceability + confidence, for when document extraction ships)
→ `Negotiation` → `NegotiationMessage`.

## Approvals

`ApprovalRequest` (generated by the policy engine only) → `ApprovalStep` (sequenced, `requiredRoleKey`,
`decidedByUserId`, `versionSnapshot`).

## Orders & fulfillment

`PurchaseOrder` → `PurchaseOrderLineItem`, `PurchaseOrderStatusEvent` → `Receipt` → `ReceiptLineItem` ·
`Invoice` → `InvoiceLineItem`, `InvoiceMatchException` (three-way match discrepancy types — architected, not yet
populated by any matching job).

## Savings & intelligence

`SavingsRecord` (one per purchase request; `negotiatedSavings` / `benchmarkSavings` / `realizedSavings` are kept
as distinct fields so the dashboard never conflates them) · `PriceBenchmark` (rolling category aggregates —
architected, not yet populated by a background job).

## AI & audit

`AIActivityLog` (every AI call, any feature/provider) → `AICorrection` (human corrections, original value never
overwritten) · `AuditLog` (every state-changing action: actor, action, entity, before/after JSON).

## Notifications & documents

`Notification` (schema ready; nothing writes to it yet) · `Document` (generic polymorphic attachment via
`entityType`/`entityId` plus typed back-relations for supplier/quote/PO/receipt/invoice; no upload endpoint wired
up yet).

## Background jobs

`Job` (type, status, `payload` JSON, `attempts`/`maxAttempts`, `lastError`, `runAt` for backoff) — see
`src/lib/jobs/queue.ts`.

## Numbering

`Organization.prNumberSeq` / `rfqNumberSeq` / `poNumberSeq` (+ matching `*Prefix` fields) are per-org sequential
counters incremented transactionally — see `src/lib/numbering.ts`.

## Multi-tenancy

Every tenant-scoped model carries an explicit `organizationId` column and index. There is no database-level
row-security under the SQLite dev provider — isolation is enforced at the application layer and verified by
`tests/tenant-isolation.test.ts`. See ARCHITECTURE.md for the Postgres + RLS hardening path.

## Migrations

Local dev uses `prisma db push`. Once this schema ships to a shared/production environment, switch to
`prisma migrate dev` / `prisma migrate deploy` so schema changes are versioned migrations, not ad hoc pushes.
